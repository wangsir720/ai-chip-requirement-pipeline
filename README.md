# AI 算力卡需求治理与适配验证管道

> 输入多源原始需求文本，自动完成**清洗去重 → 字段抽取 → 适配判定 → 测试脚本生成 → 知识库沉淀**，
> 输出结构化需求单、适配矩阵、测试脚本、流转看板与需求管理 SOP。
>
> **需求样本为自拟、非真实业务数据；全部判定基于公开资料，未做真卡实测。**

零第三方依赖，`git clone` 后直接跑。

---

## 1. 为什么做这个

AI 算力产品的需求池长这样：邮件、工单、会议纪要混在一起，
同一个问题被不同人用不同措辞报三四次，字段缺一半，能装下的卡和模型完全看不出来。

于是产生三个具体后果：

1. **重复消耗研发工时** —— 同一个算子适配问题被当成三个需求派三次；
2. **需求单不可执行** —— 「客户说跑不起来」这种描述，研发无法判断该查显存还是查算子；
3. **踩过的坑反复踩** —— 问题解决了但没沉淀，下个月换个客户再问一遍。

这个工具做的事是：**把「杂、乱、散」的原始需求，变成字段完整、判定有据、可执行、可追溯的需求单**。

它对应 JD 三条职责：

| JD 职责 | 本项目落点 |
|---|---|
| 职责 1 · 全生命周期管理，录入/审核/清洗/分析/拆解 | `cleaner.py` + `extractor.py` + 分析报告 |
| 职责 2 · 跨部门协同，跟踪流转状态，同步进度与风险 | `doc_assembler.py::render_board` 状态看板 + 风险同步 |
| 职责 3 · 流程标准化，SOP + 工具集 + 问题闭环知识库 | `doc_assembler.py::render_sop` + `kb_builder.py` + `script_gen.py` |

## 2. 核心设计决策

### 2.1 去重不用文本相似度，用结构化去重键

这是本项目最重要的一个决策，也是实测逼出来的。

最初的实现用 bigram Jaccard 相似度去重。实测本项目样本集：

| 类别 | 相似度区间 |
|---|---|
| 同义重复对（如 RAW-002 / RAW-006，同一问题不同措辞） | **0.130 – 0.303** |
| 不同诉求对（如 RAW-001 / RAW-002，同卡同模型但诉求不同） | **0.086 – 0.140** |

**两个区间重叠** —— 无论阈值调在哪都会误判。这不是调参问题，是方法选错了。

改用**结构化去重键：芯片 + 模型 + 首要问题类型**。依据是产品语义：
同一张卡 + 同一个模型 + 同一类问题 = 同一个需求，不管它来自哪个渠道。

两个有意的设计：

- **框架不参与去重键** —— 实测 RAW-002 写「vLLM」、RAW-006 未提框架，实为同一需求；
- **多标签问题类型只取首要标签** —— 一条需求常同时命中「显存不足」与「能力咨询」，
  取首要标签（按规则优先级），否则同一需求因标签集不同而漏合并。

结果：15 条 → 11 条，合并 4 条，**零误合并**。

### 2.2 责任对等原则：`unverified` 来源不参与判定

需求池里「PyTorch 2.1 算子 fallback 了」这句话来自客户单方描述，
来源可信度是 `unverified`。引擎据此**只输出「需实测验证」，不输出「不推荐」** ——
拿客户单方描述去否定一个框架版本，责任不对等。

这条规则由 `tests/test_validator_kb.py::test_unverified_fallback_never_yields_not_recommended` 强制。

### 2.3 字段必须带原文出处

抽到的每个技术字段都记录原文字符区间。没有出处的字段等于编造。

`customer_industry` 明确标注「样本自带（非原文抽取）」——
不从原文猜行业是硬纪律，因为猜出来的字段会被下游当成事实使用。

字段完整率因此是**可测的**：完整率 = 有出处的必填字段数 / 5。

### 2.4 阈值一律留空

生成的测试脚本里 `THRESHOLD = None`。本项目没有客户模型，任何阈值数字都只能是编的。
测试 `test_threshold_is_never_fabricated` 强制阈值说明里不出现具体数值。

## 3. 数据源与合规边界

| 数据 | 来源 | 可信度 |
|---|---|---|
| 芯片型号与产品线 | 公司官网产品页 | `secondary` |
| 模型参数量与显存量级 | 公开模型卡 | `secondary` |
| 框架适配与迁移路径 | FlagOS 生态官方仓库、公开技术资料 | `official` / `secondary` / `unverified` |
| 原始需求样本 | **自拟** | — |

`credibility` 三级定义与逐条来源见 `data/sources.md`。

**明确不含**：真实客户名称、合同金额、账号凭据、内部报价、客户业务数据。
样本中的公司一律写「客户」，行业只用通用分类（政务 / 金融 / 能源 / 医疗 / 互联网）。

### 样本构造说明

15 条样本有意混合四种来源（email 5 / jira 4 / meeting_note 3 / ticket 3），
并埋了 9 类「脏」：完全重复、同义重复、多问题混杂、字段缺失、指代不明、
口语化噪声、同一诉求多问法、诉求不完整、同产品不同代混淆。
逐条对照见 `data/raw_requests/README.md`。

## 4. 方法

```
data/raw_requests/multi_source_demo.json
        │
        ├─ cleaner.py ────── 归一化 → 去噪声（留痕）→ 指代标记
        │      │              ↓
        ├─ extractor.py ──── 字段抽取（每个字段带原文字符区间）
        │      │              ↓
        ├─ cleaner.py ────── 按结构化去重键合并
        │      │              ↓
        ├─ validator.py ──── 四档判定：支持 / 需实测验证 / 不推荐 / 待人工核实
        │      │              ↓
        ├─ script_gen.py ─── 测试脚本骨架（CPU 模拟模式可跑）
        │      │
        └─ kb_builder.py ─── 闭环五要素校验 → 入库 / 拒收 + 四维索引
                       │
     doc_assembler.py ───┴── 需求单 / 分析报告 / 看板 / SOP
```

管线顺序**必须**是「清洗 → 抽取 → 去重」：去重键依赖抽取出的字段。
（早期实现顺序写反，导致去重率恒为 0 —— 这个坑记在 `cleaner.py::run_pipeline` 的注释里。）

## 5. 快速开始

环境：Python 3.10+（验证于 3.12.8 / Windows）。**无需安装任何运行时依赖。**

```bash
# 跑全流程，生成全部产物
python -m src.cli

# 实际运行一个生成的测试脚本（验证 CPU 模拟模式真能跑）
python -m src.cli --verify

# 知识库检索：按芯片 / 模型 / 框架 / 问题类型
python -m src.cli --search chip_model TX8
python -m src.cli --search issue operator_fallback

# 跑测试
pip install pytest
python -m pytest -q
```

输出落在 `output/`：

| 文件 | 内容 |
|---|---|
| `requirement_specs.md` | 11 张结构化需求单，每张字段带原文出处 + 清洗留痕 + 重复来源 |
| `analysis_report.md` | 需求分析与拆解报告：总量质量、分布、判定汇总、**字段缺失清单** |
| `matrix.csv` | 适配矩阵，可直接贴进工单系统 |
| `board.md` | 流转状态看板 + 风险同步（每个状态对应明确下一动作） |
| `sop.md` | 需求管理 SOP，**每条规则标注实际实现位置** |
| `knowledge_base.json` | 问题闭环知识库 + 四维倒排索引 |
| `scripts/verify_*.py` | 测试脚本骨架，CPU 模拟模式可直接跑 |
| `result.json` | 全量结构化结果 |

## 6. 实测输出

```text
$ python -m pytest -q
.............................................................            [100%]
61 passed in 2.08s

$ python -m src.cli
原始需求 15 条 → 唯一 11 条（去重 4 条，26.7%）
必填字段平均完整率 78%
适配判定：需实测验证 4 / 不推荐 3 / 待人工核实 4
知识库入库 3 条，拒收 0 条，待解决 8 条
测试脚本 7 个，跳过 4 个

$ python -m src.cli --verify
运行样例脚本：verify_RAW-003.py
exit=0
{ "mode": "simulated", "batch": 1, "seq": 512,
  "check": { "verdict": "未标定", "reason": "THRESHOLD 为 None —— 阈值须按实际模型标定后判定" } }
```

**「支持」档为 0 条是一个真实且重要的结果**，不是 bug：

显存最充裕的组合是 `TX8 + YOLOv8n-detect`（4 GiB / 32 GiB，余量 85%），
但它同时命中 `PyTorch 2.1 算子 fallback` 的记录 —— 而该记录是 `unverified` 级。
按 §2.2 的责任对等原则，引擎把它降为「需实测验证」而不是「支持」。

**换句话说：显存够 ≠ 能跑。** 这正是适配验证要回答的问题，
也是这个工具相对「只算显存」的价值所在。

其余判定分布：

| 判定 | 条数 | 典型原因 |
|---|---|---|
| 需实测验证 | 4 | 显存够但余量 < 15%，或有 unverified 级的算子行为记录 |
| 不推荐 | 3 | 模型权重下界超单卡显存（DeepSeek-V3 需 1400 GiB / 32 GiB） |
| 待人工核实 | 4 | 字段不全，或芯片公开资料未查到显存（REX81） |

## 7. 已知局限

| # | 局限 | 影响 | 补齐方式 |
|---|---|---|---|
| 1 | **无真卡实测** | 全部判定基于公开资料与自拟样本 | 拿到实机后按 `scripts/` 里的骨架实测 |
| 2 | **阈值未标定** | 脚本只产出测量数据，不判定通过与否 | 须按客户实际模型与 SLO 标定 |
| 3 | **需求样本自拟** | 去重率、完整率等指标不代表真实需求池 | 拿到真实 Jira 导出数据后重跑（CSV 结构不变） |
| 4 | 显存需求为**下界** | 未计入 KV Cache 与激活值，长上下文场景会低估 | 需按目标模型结构参数精算 |
| 5 | 芯片详细规格未公开 | 可重构架构的算力/带宽/互联数据缺失，REX81 因此判待核实 | 需厂商规格书 |
| 6 | 抽取走正则规则 | 复杂表述（嵌套否定、多语言混写）可能漏抽 | 规则可扩充，但须同步补测试 |
| 7 | 知识库仅 3 条 | 样本中多数需求属「待核实」，本就未闭环 | 真实场景下随问题解决逐步积累 |

第 1、2 条是本项目最大的短板：**这个工具验证的是「需求治理方法论与判定口径是否站得住」，
不是「某张卡跑某模型的真实性能」。** 前者现在就能做，后者必须有硬件。
