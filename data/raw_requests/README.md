# 原始需求样本集 · 构造说明

> ⚠️ **本目录全部样本为自拟，不含任何真实客户信息。**

## 为什么需要样本

JD 职责 1 的原话是「解决多源需求杂、乱、散的问题」。要证明清洗器有用，
就得先有一批**真的杂乱**的需求。这个目录就是为此构造的输入。

## 构造逻辑

`multi_source_demo.json` 含 15 条原始需求，有意混合了四种来源，因为真实需求池就是这样：

| 来源 | 条数 | 真实场景特征 |
|---|---|---|
| `email` | 5 | 口语化、有背景铺垫、夹带多个问题、语气随意 |
| `jira` | 4 | 相对规范，有复现步骤与期望，但字段常缺 |
| `meeting_note` | 3 | 多人转述、指代不明（「这个卡」「他们那边」）、带时间与人员 |
| `ticket` | 3 | 极短、只有现象无环境、术语堆砌 |

## 每条样本有意埋的「脏」

清洗器要处理的问题，全部在样本里真实存在：

| # | 脏数据类型 | 样本编号 | 具体表现 |
|---|---|---|---|
| 1 | **完全重复** | RAW-002 / RAW-006 | 同一问题，文字表述几乎一致，来源与上报人不同 |
| 2 | **同义重复** | RAW-003 / RAW-007 / RAW-009 / RAW-015 | 同一问题（PyTorch 2.1 算子 fallback），四次不同转述 |
| 3 | **多问题混杂** | RAW-001 | 一条里塞了 OOM、batch 上限、70B 支持、文档四个诉求 |
| 4 | **字段缺失** | RAW-006 | 无客户行业（实际上有，藏在 `customer_industry` 字段外） |
| 5 | **指代不明** | RAW-001 / RAW-005 / RAW-007 | 「这个卡」「他们那边」「这个肯定跑不了吧」 |
| 6 | **口语化噪声** | RAW-005 | 「。。。」「吧」「不太懂」 |
| 7 | **同一诉求多问法** | RAW-004 / RAW-010 / RAW-014 | REX81 交付与扩展能力，三种问法 |
| 8 | **诉求不完整** | RAW-011 | 「需要几张卡」没有模型名与精度 |
| 9 | **同产品不同代混淆** | RAW-008 / RAW-013 | TX81 模组与 TX5 芯片被混为一谈 |

**期望的清洗结果**：15 条 → **6 个唯一诉求**。具体去重结果由 `cleaner.py` 计算，
可用 `python -m src.cli` 复现，不在此处预写结论（避免与实现脱节）。

## 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 原始编号（`RAW-` 前缀） |
| `source` | string | 来源渠道：`email` / `jira` / `meeting_note` / `ticket` |
| `received_at` | string | 接收日期（YYYY-MM-DD） |
| `text` | string | **需求原文**。字段抽取的唯一切入点 |
| `reporter` | string | 上报人 / 角色 |
| `customer_industry` | string | 客户行业 |

> `reporter` 与 `customer_industry` 是**样本自带的上下文**，不是从 `text` 抽取的结果。
> 清洗器不从 `text` 里猜行业 —— 抽不到就填「未提取到」，这是项目的核心纪律之一。

## 不影射真实客户

样本中的公司名、客户名、具体项目名**一律不出现**。涉及的公司一律写「客户」，
行业只用通用分类（政务 / 金融 / 能源 / 医疗 / 互联网）。
技术栈信息（芯片型号、模型名、框架版本）取自**公开产品资料**，不涉密。
